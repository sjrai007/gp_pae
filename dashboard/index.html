Why three layers, not one

Each layer catches a class of bug the others structurally cannot. That is not a theoretical claim — the three bugs below were each caught by a different layer, and the third would have survived the other two indefinitely.

Layer 1

RTL vs. software model

A from-scratch OCaml interpreter of the instruction set runs in lockstep with the hardware. Every register, pin and FIFO compared every cycle. Catches RTL that disagrees with the architecture.

Layer 2

Two independent simulators

The same scenario runs through Hardcaml's simulator and, separately, through Icarus Verilog against the generated Verilog. A bug has to fool two independently written engines to survive.

Layer 3

Decode the waveform

Read the emitted pin trace back as a protocol frame and check it spells the byte we sent. The only layer that can catch microcode whose timing is wrong but self-consistent.

Bugs caught, and by what

Shift register grew without bound

hardcaml/lib/isa.ml · the software model

The model accumulated input bits with an unmasked shift, so after repeated IN instructions its value drifted past 8 bits — while the real hardware, being a fixed 8-bit register, silently truncated.

Caught by: tracing the hardware's register width against the model before either had run. A latent mismatch that would have produced confusing failures later.

Register reads returned the previous transaction

hardcaml/lib/config_port.ml · the SPI config port

Read data was latched on the same clock edge that updated the address register, so a read always returned whatever the last transaction had addressed. A register cannot see its own not-yet-applied update through combinational logic downstream of it.

Caught by: layer 2 — an integration test that wrote a register over the real SPI port and read it straight back.

Every UART bit ran one cycle long

hardcaml/test/test_gp_pae.ml · the UART TX microcode

The loop-closing jump costs a real clock cycle even when it is not taken, and that cycle was not budgeted out of the bit-period delay. The hardware and the software model agreed with each other perfectly — both faithfully executed the same wrong microcode, so cross-checking them proved nothing.

Caught by: layer 3 only — decoding the emitted waveform gave 0x4D where 0xA5 was sent. This is the bug that justifies the whole third layer.

Still to come in Phase B: randomized property-based testing (thousands of generated byte/timing combinations per protocol rather than hand-picked cases), and a formal check on FIFO invariants using Yosys' SAT solver.

What is on the die

Four independent sequencer lanes, a pin crossbar that any lane can be pointed through, a shared flag register for cross-lane handshakes, and an always-live SPI port for programming. The field

Several entries are already public. The most developed one independently arrived at almost exactly our architecture — four lanes, a 16-bit instruction word, an SPI slave host interface, flip-flop instruction memory. When two teams converge that precisely with no contact, the architecture is the obvious answer and architecture alone will not distinguish anyone. Execution, measurement and area efficiency will.

Where we intend to be different

Logic-analyzer mode

Queued

A lane running an input-only loop is a logic-analyzer channel with a host FIFO — the same silicon, no new hardware, just different microcode. The brief frames this chip as a tool for “hardware debugging and reverse engineering”, so a capture mode answers the brief's own stated purpose rather than adding a feature next to it.

JTAG and SWD

Queued

Named in the brief and skipped by the leading public entry. JTAG's 16-state TAP controller is a natural fit for a branchy little sequencer — arguably an easier target than SPI. SWD needs the same runtime pin-direction flipping I2C already uses.

Design-space exploration

Queued

The design is a generator, not a fixed netlist: lane count, memory depth and instruction width are parameters. So we can sweep the grid, synthesize every point and publish the actual area/functionality frontier — choosing parameters from measurement while hand-written entries choose from intuition.

Non-uniform lanes

Queued

Complex protocols need deeper program memory, but only one or two lanes run them at a time. A generator emits one deep lane and several shallow ones from a parameter list; in hand-written RTL that is a copy-paste refactor, so most teams will make every lane deep and pay for it everywhere.

Property-based testing

Queued

Replace hand-picked test cases with thousands of generated ones: random bytes, random clock-stretch durations, jittered edges. For I2C there is a sharp invariant to assert — stretching the clock may change when a byte arrives but never what it is.

Formal FIFO proof

Queued

A bounded SAT proof that the host FIFO invariants hold, rather than testing that they happened to hold on the traces we tried. Cheap to add and matches a technique a competing entry already demonstrated.

One constraint discovered while designing the protocols, worth deciding early: the chip has only four shared flags, and running SPI and I2C at the same time already consumes all four. Any additional protocol needing cross-lane coordination means either reusing a flag carefully or widening the register — a hardware change, not a microcode one.

What the budget and the clock actually are

6×4 tiles

Tiny Tapeout puts many independent projects on one shared die and multiplexes them onto a common set of I/O pins. A tile is the unit of floor space each project rents. 6×4 means a rectangle 6 tiles wide and 4 tall — 24 tiles. The rules put a tile at roughly 200×150 µm, so the allocation is about 0.7 mm², and suggest budgeting ~1,000 logic cells per tile.

That ~24,000-cell figure is where the budget number on this page comes from. It is guidance for planning, not a hard gate — the real constraint is whether the design places and routes inside the rectangle, which only the full flow answers.

50 MHz

Worth being straight about: this is not a derived or verified number. It is the Tiny Tapeout template's out-of-the-box default — CLOCK_PERIOD: 20 nanoseconds in the hardening config — carried through unchanged. No static timing analysis has run, so whether the design actually closes at 50 MHz is unknown.

Two real constraints sit around it. Tiny Tapeout's I/O is rated to about 33 MHz on outputs, so pins cannot be toggled at full core speed regardless. And 10BASE-T at 10 Mbit leaves only 5 core cycles per bit — tight for a CPU that needs at least one cycle per instruction, and the strongest argument for raising the clock if timing allows.

Flip-flops cost roughly 5–6× the area of a basic gate, so the cell count above understates how much silicon the registers actually occupy. Instruction memory is plausibly 40–50% of the whole chip — which makes it the one thing worth optimizing.

Three levers on instruction memory

The leading public entry documented flip-flop instruction memory as a known limitation and left it there. It is the dominant area term for everyone who built this architecture — which, judging by the public entries, is everyone.

To be precise about why this matters. Area is not itself a judging criterion — the stated criteria are unique functionality and novel design/verification methodology, and the only hard area requirement is fitting inside 6×4 tiles, which the design already does with room to spare. Instruction memory matters because it is the currency: every flip-flop freed there buys a lane or a protocol that a competitor spending the same silicon on oversized program memory cannot fit. The goal is functionality per tile, not the smallest possible chip.

Memory selection

The rules themselves recommend SRAM over flip-flops for instruction memory. Researched, and deliberately deferred rather than dismissed — the numbers are here so the decision stays visible and can be revisited on measurement rather than memory.

Why not simply switch

The density win is real; so are three costs.

FactorFlip-flopsSRAM macro
Density per bit~22 µm² (est.)2.6–3.7× better
Read behaviourCombinational, same cycleRegistered, 1 cycle later
Fetch for 4–5 lanesPrivate per lane, no arbitrationOne port, needs arbitration
Timing determinismGuaranteed by constructionMust be proven under contention
Flow integrationNone neededCustom placement, power grid, DRC/LVS waivers

The usual objection — one port cannot feed five lanes — is actually wrong here, because bit-banging is overwhelmingly idle: at real baud rates a lane fetches on under 5% of cycles. The genuine difficulty is that protocol timing must stay cycle-exact, so contention can never cause a variable stall. That is real work, which is why it comes after the cheaper levers, not before.

Honest status of these numbers. The 83.2% figure is exact arithmetic from the design parameters. Cell counts are real, from generic Yosys synthesis. Everything in µm², and the flip-flop-to-gate area ratio, is an estimate — the IHP PDK is not installed locally, so mapped area, timing and power only become measured in Phase C. Power has not been analysed at all yet; the largest expected win is clock-gating the instruction memory, which is written once at programming time and then never again, yet currently clocks 50 million times a second.
